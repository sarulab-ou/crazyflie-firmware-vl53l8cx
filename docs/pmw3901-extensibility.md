# PMW3901 を用いた実装の拡張性

Flow deck の光学フローセンサー PMW3901 について、
「現在取得しているピクセル移動量以外に何が取れるか」
「VL53L1x の代わりに VL53L8CX を組み合わせる価値はあるか」
「その他どんな拡張可能性があるか」を検討した結果のまとめ。

## 1. ピクセル移動量以外に取得できるデータ

### 1.1 motion burst で既に読んでいるが活用が薄いもの

現在の実装はレジスタ 0x16 からの motion burst（12 バイト）を一括読みしており、
`motionBurst_t` には deltaX/Y 以外のフィールドも既に含まれている:

| フィールド | 内容 | 現在の活用状況 |
|---|---|---|
| `squal` | 追跡できた特徴点数（surface quality） | ログのみ。EKF のゲーティングには未使用 |
| `shutter` | 露光時間（テクスチャの少なさの指標） | `motion.adaptive` パラメータ有効時のみ測定ノイズ推定に使用（デフォルト OFF、`flowdeck_v1v2.c:111-125`） |
| `rawDataSum` / `maxRawData` / `minRawData` | フレーム輝度統計 | ログのみ。照度低下・白飛び検出に使える |
| `observation` | チップ内部状態の監視用 | 完全に未使用 |

### 1.2 モノクロ画像データへのアクセス — 可能

PMW3901 には **frame capture モード**があり、内部で相関計算に使っている
**35×35 ピクセルのグレースケール生画像**を SPI で読み出せる
（RawData_Grab (0x58) / RawData_Grab_Status (0x59) を使った画素順次読み出し。
Bitcraze コミュニティに実装例あり）。

ただし重大な制約が 2 つある:

1. **フロー出力と排他**: frame capture モード中はモーション出力が停止し、
   復帰にはレジスタ再初期化（`InitRegisters()` 相当）が必要。飛行中の併用は実質不可。
2. **読み出しが遅い**: 画素ごとのレジスタポーリングのため、1 フレームに数百 ms〜秒オーダー。
   リアルタイムビジョンには使えない。

→ 用途は「地上での路面テクスチャ診断」「取り付け・レンズ汚れ確認」「離陸前の路面分類」など
オフライン的なものに限定される。リアルタイム画像処理が必要なら AI deck（GAP8 + カメラ）の領域。

## 2. VL53L1x の代わりに VL53L8CX を使う価値

### 2.1 理論上のメリット（現行 `mm_tof.c` の弱点がそのまま改善候補）

| 現状の弱点（VL53L1x 1 点測距） | VL53L8CX（4×4 / 8×8 ゾーン）での改善 |
|---|---|
| 傾き補正が `z/cos(α)` 近似＋FoV コーンの 7.5° 控除というヒューリスティック（`mm_tof.c:36-40`） | 16 ゾーンの距離から**床面を平面フィット**すれば、傾きと対地高度を幾何学的に直接解ける |
| 家具の縁などの段差で高度推定がジャンプ | ゾーン間の距離不連続で**段差を検出**し、更新棄却 or 分散増大のゲーティングが可能 |
| 84° 以上傾くと更新停止（`R22 ≤ 0.1` で棄却） | FoV 内の複数ゾーンから信頼できる方向を選択できる |
| 床が斜面だと誤差 | 平面フィットで斜面の法線まで推定でき、`mm_flow` の「真下は平坦」仮定の補正にも使える |

さらに好都合な点:

- **PMW3901 の画角 42° と VL53L8CX の画角 45° がほぼ一致**する。
  フローの観測式は v/z を含むため、「フローカメラが見ているまさにその領域の深度マップ」が
  得られるのは原理的に相性が良い。
- レートも 4×4 モードなら 60 Hz まで出せ、現行 zranger2 の 40 Hz（25 ms 周期）より速い。

### 2.2 コスト・デメリット

- ファームウェア blob が約 85 KB のフラッシュを消費。ドライバの RAM 要求も大きい
  （本リポジトリで既に CCM 退避 `vl53l8cx_USE_CCM` で対処している通り）。
- 消費電力が VL53L1x より大幅に大きい（VCSEL 照射面積が広い）。
- 8×8 モードは 15 Hz に落ちるため、実用は 4×4 モード。
- 1 点あたりの測距ノイズは専用 1 点センサーより不利な場面がある。

### 2.3 結論

**「単なる高度計の置き換え」なら割に合わないが、平面フィットによる傾き・段差補正まで
実装するなら明確に優位性がある。**

本リポジトリでは VL53L8CX 11 個がまだ EKF 未接続（ログのみ）なので、最小の第一歩は
下向き 1 個の中央ゾーン平均（または target_status で有効判定したゾーン平均）を
既存の `estimatorEnqueueTOF()` に流すこと。既存の `mm_tof` がそのまま使える。

## 3. その他の拡張可能性

### 3.1 すぐ手が届くもの（ソフトのみ）

- **適応測定ノイズの本格運用**: `squal`/`shutter` ベースの適応 std
  （`useAdaptiveStd`）の係数は Bitcraze の実験フィットのまま。
  自分の環境（路面・照明）で再フィットする価値がある。
- **動的ゲーティングの強化**: 現状のゲートは `motion == 0xB0` と外れ値 100 px のみ。
  `squal` が低い区間で `stdFlow` を吊り上げる、あるいは更新自体を棄却する処理を追加できる。

### 3.2 ハード追加を伴うもの

- **PMW3901 の 2 個搭載 → ヨー観測**:
  1 個のフローセンサーはカメラ光軸まわりの回転（ヨー）を原理的に観測できない
  （回転流は平均するとゼロ）。しかし機体中心からオフセットして 2 個置けば、
  レバーアーム効果の差分から**ヨー角速度・ヨー角の観測**が作れる。
  現在の Flow + ToF 構成ではヨーが完全にジャイロ積分頼みでドリフトし続けるため、
  実用価値が大きい。観測モデルは `mm_flow.c` のレバーアーム項
  （`flowdeckPos`, `mm_flow.c:72-77`）が既に片鱗を実装している。
- **上向きフロー**: 天井テクスチャでのフロー。床が水面・鏡面・無地の環境での冗長系。
- **VL53L8CX 11 個との深い統合**:
  16 点 × 11 = 176 点の粗い 3D 点群が毎フレーム得られる。
  既知マップに対する `mm_distance` 型の更新（壁までの距離観測）や、
  廊下・部屋での壁面平面フィットによる水平位置ドリフト補正（簡易 SLAM 的な使い方）まで
  視野に入る。フローが苦手な「長時間の位置ドリフト」を補う位置の絶対観測になり得る。

### 3.3 センサー自体の世代交代

- PixArt の後継品 **PAA3905** は同系統のフローセンサーで、
  低テクスチャ路面の自動検出モード、より広い動作照度、同様の frame capture を持つ。
  PMW3901 とレジスタ互換ではないがドライバ構造はほぼ流用でき、
  路面適応性の根本改善を狙うならセンサー置き換えも選択肢。

## 4. 推奨する拡張の優先順位

効果とコストのバランスで、以下の順を推奨する:

1. **VL53L8CX 下向きセンサーを EKF に接続**（既存 `mm_tof` + `estimatorEnqueueTOF()` で済む）
2. **平面フィットで傾き・段差補正**（`mm_tof` の cos 近似を置き換え／段差ゲーティング）
3. **squal 適応ゲーティング**（ソフトのみ、低テクスチャ路面での堅牢化）
4. **2 個目の PMW3901 でヨー観測**（ヨードリフトの根本対策）
